# Transient HTTP Troubleshooting

Read only after a transient selection, exhaustion, generated-variant, or fallback check fails.

Start the dependency mock in debug mode and send the distinctive downstream request directly. Confirm the transient
example—not a contract-generated response—is selected, then check delay ordering and matcher exhaustion.

Schema-resiliency may generate several valid values for one request. Give the scenario one fixed correlation field and
track each generated enum or boundary value with `value: each, times: 1`, or literal expectations when a matcher cannot
preserve bounds. Validate examples and directly probe representative requests before rerunning the complete suite and
usage checks.

After exhaustion, a non-strict mock may generate contract-valid data that violates cross-field application rules. Add a
correlated normal expectation or constrain fallback values without weakening application validation.

For stateful cases, capture the identifier or location created by the public initiation and substitute it into the
follow-up within one bounded behavior. Never use a fixed unrelated ID or execution order. Reset mock and workflow state
between independent runs.
